# Audit 2026-11: Phases 0–6 (HEAD `ef6bca4`)

Done on 2026-11-05, before the redesign. Two independent, read-only auditors (Claude Fable 5.1 at
maximum effort) read everything from Phase 0 to `ef6bca4`, code and docs:

- **Auditor A, security and privacy**: role checks on every page, action and handler; object-level
  authorization; the Better Auth setup; Zod and size limits; raw SQL; rate limits; storage;
  secrets and personal data in bundles, logs and errors; headers and CSP; cron and health;
  the Anthropic calls; the GitHub workflows; `pnpm audit`; the data rules; /privacy vs what is stored.
- **Auditor B, correctness and data**: ranking math and eligibility vs docs/04; trust, panel,
  burst and abuse rules; re-rating; matching vs docs/05; menu parsing and the review queue; claims;
  merge; the Overture sync; the nightly jobs; schema vs migrations; query plans on the demo data;
  races; time zones; ISR; errors and 404s; SEO; the deploy check; docs vs code; the tests.

Rules of the audit: no edits, no commits, no production access, only `SELECT`/`EXPLAIN` on the
local database (demo data from `pnpm dev:demo`, removed afterwards). Every finding below was then
checked by hand against the code (and the libraries in `node_modules` where a claim depended on
them) before anything was changed. Nothing was committed: the fixes are in the working tree, grouped
below as suggested commits.

## Findings

### High

**A-01 · fixed · A banned user could erase the ban by deleting the account and signing in again.**
`src/server/services/account.service.ts`. `deleteMyAccount()` checked only the role and the
"DELETE" confirmation; `deleteAccountTx()` hard-deletes every rating (HIDDEN ones included) and the
User row, and the next Google sign-in creates a fresh user with trust 0.6. Scenario: an admin bans a
shill from /admin/review; the shill deletes the account on /me and is back two minutes later, clean.
Fix: a banned account answers `403 USER_BANNED` on deletion (an admin deletes it by hand; /privacy
says so). Test: `tests/unit/account/account-db.test.ts` "a banned account cannot delete itself".
A hashed list of banned Google accounts, consulted at sign-up, is left as an open question.

### Medium

**A-02 · fixed · After account deletion a claimant's phone number and proof note, and a dispute's
contact, stayed in decided review items.** `src/server/repositories/account.repo.ts`. Only OPEN
items the user filed were deleted; decided ones kept their payload (shown on /admin/review under
resolved/rejected and present in every backup) although /privacy promised "without your name".
Fix: decided `OWNER_CLAIM` and `FLAG` items of the user have `phone`, `proofNote` and `contact`
blanked and `redacted: true`; /privacy says so. Checked in the account deletion test.

**A-03 · fixed · The backup's TLS did not verify the server.** `scripts/db-backup.sh`. libpq's
`sslmode=require` encrypts but accepts any certificate, so a party between GitHub's runner and
Supabase could read the whole dump every night. Fix: the script removes any `sslmode` from the URL
and runs `pg_dump` with `PGSSLMODE=verify-full` and `PGSSLROOTCERT=config/supabase-root-2021.crt`
(the same root CA `src/server/db-ssl.ts` verifies with; a unit test keeps the two copies equal).
`BACKUP_SSLMODE` overrides the mode (used with `prefer` for a plaintext local run, which was done:
the script dumps, encrypts, decrypts and compares; in its default mode it refuses a plaintext
server). The URL still sits in `pg_dump`'s argv on the runner (single-tenant, ephemeral): accepted.
**Owner to-do**: watch the first backup run; if the certificate check fails against the pooler,
set `BACKUP_SSLMODE=require` in the workflow and report it.

**B-01 · fixed · `logEvent` fields overwrote the event name.** `src/server/log.ts`. The line was
`{ at, action, ...fields }`, so review decisions were logged as `"release"`/`"hide"` instead of
`admin.review.resolve`, and every unexpected action failure as the action's name instead of
`action.error`. Fix: the event name and `at` are written last; the two call sites use `decision`
and `name`.

**B-02 · fixed · A merge deleted a pending claim but moved its OPEN review item, which could then
never be decided.** `src/server/services/restaurant.service.ts`, `claim.service.ts`. A source
claim by a user with any claim on the target is dropped, but its item followed the open items to
the target; approve and reject both answered `ITEM_CHANGED` for good. Fix: the merge closes those
items as rejected duplicates (`closeOpenClaimItems`), and an item whose claim no longer exists can
always be rejected.

**B-03 · fixed · A comment-held rating on a STALE row never revived the row.** `src/server/services/review.service.ts`.
The revive happened only for a rating that was ACTIVE at write time; after the admin released a
held one, the row stayed STALE: counted in the score but invisible on the ranking page. Fix: a
release revives the STALE rows of the released ratings (`reviveStaleDishRows`, under the row locks).

**B-04 · deferred · The nightly recompute runs one transaction per rated row.** About 11 round
trips each; at the ~10k rated rows of the month-4 target it nears Vercel's 300 s. Dozens of rows
today. Open question: a set-based step 3, or a checkpointed JobRun, measured on a 10k-row fixture.

## What the auditors checked and found sound

Role checks on every admin and owner page, layout, action and handler, with the services re-checking
the actor; object-level authorization on ratings, uploads, menus, claims and owner pages; the
Better Auth setup (cookie attributes, cookie cache off, `role` not settable, e-mail/password, user
deletion and e-mail change off, the beta gate on every sign-up path, the callbackUrl rules);
Zod on every input with caps; every raw SQL site parameterised, LIKE patterns cleaned; rate limits on
every write and search with keyed IP hashes and a single-statement bucket increment; storage (SigV4
presigning, server-chosen keys, HEAD checks, the Upload row ownership, the clean-up's re-check under
the share lock); no secrets or server code in client bundles; the CSP and headers on every response;
cron fail-closed with a constant-time compare; the Anthropic caps (50 parses a day under a lock, 25
matcher calls, output bounded, candidates only); the workflows' permissions and secret masking; `pnpm
audit` with one low advisory (deepmerge, via the shadcn CLI) and the overrides in place; the data
rules (no scraping, no Google Places, Meta and Microsoft only, credit page) with the dev database
showing 0 Google links and only those two sources; /privacy matching what is stored.

Ranking math and eligibility exactly as docs/04 in TypeScript and SQL; the trust table and its
order; panel limits; the burst and comment rules with their tested false positives; re-rating and
history with the decay clock untouched by status changes; matching as docs/05 with the seed
invariants; menu parsing and the exactly-once REVIEWED transition; claims and the owner area; the
merge rules step by step; the Overture filters, refresh rules and idempotent re-run (2784 candidates,
0 Google links); the nightly order, the overlap refusal and the Sunday snapshot; schema, 17
migrations and docs/03 in step (one line, fixed); every hot query with an index (plans run on the
demo data); the lock order of docs/02 followed by every writer; time zones; ISR pages reading no
request data; errors never leaking; SEO (noindex on thin pages, sitemap, JSON-LD without
aggregateRating); the deploy check; every CLAUDE.md command real.

Not covered (both reports say so): behaviour at scale was inferred from SQL and indexes, not
measured (the demo database is small); no write path, cron or race was executed; Vercel's handling
of a client-sent `x-real-ip` is platform behaviour (hence A-15's fix).
